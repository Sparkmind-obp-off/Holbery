# HOLBERY — Launch and Operations Template

Parent HOLBERY; apply to a controlled pilot before broad release.

## Pre-launch gates

Offer/project ID ___; version ___; target customer ___; included/excluded scope ___; truthful status ___; accountable owner ___; legal owner/hak ___; consent/data boundary ___; tested delivery link/file ___; verified contact/support ___; pricing/tax/refund/licensing terms approved ___; budget/support cap ___; metrics/baseline ___; rollout/rollback ___; known limitations ___. Block payment/contract claims if identity/rights/terms absent.

## Pilot onboarding

1. Confirm eligible operator and privacy/consent.
2. Record current workflow/baseline without copying private data into public repo.
3. Deliver resource and show one complete task using synthetic inputs.
4. Operator performs one real task independently.
5. Schedule day-3 and day-14 check; explain support limitations and feedback method.
6. Log delivery/version/anonymized outcome in approved private space; sanitized evidence only in git.

## Launch log

Date/time ___; owner/approval ___; audience/sample ___; channel ___; artefact/version/hash ___; delivery receipt ___; known risks ___; health/test results ___; support request/action ___; next review ___. No fabricated launches or sales.

## Operate / incident

Daily: task completeness/reconciliation, blockers, safe record custody. Weekly: feedback, support minutes, errors, retention/usefulness. Incident: severity, affected scope/data, containment, owner, customer communication, rollback, legal escalation if needed, postmortem/action. Website hosting failures do not justify disclosing credentials.

## Shutdown / rollback

Preserve source version/history; stop new sales; fulfill support/refund promises; communicate actual impact; export/delete data lawfully; revoke unused accounts/secrets; stop recurring charges; update catalog/lifecycle; document final outcome. Destructive transfers/deletions require explicit authority.
