## Decision authority

Pemilik proyek HOLBERY menjadi approval authority administratif sementara; nama/entitas legal belum diverifikasi. Operating owner mengusulkan, authority menyetujui, legal adviser memeriksa hak jika diperlukan. Jangan menjadikan GitHub handle sebagai pemilik hukum semua IP.

## USE HOLBERY DIRECTLY OR CREATE CHILD BRAND

The default is **HOLBERY-native**. A Library item does not receive an independent brand merely because it is useful, named, technically substantial, or reusable. The Library is the parent layer; child branding is an evidence-based promotion decision.

1. Apakah customer dan promise konsisten dengan parent, parent trust berguna, dan tidak membutuhkan market separation? Gunakan HOLBERY + descriptor sederhana.
2. Jika parent visibility tidak memberi nilai dan penawaran kecil: nama produk deskriptif tanpa child brand baru.
3. Pertimbangkan child jika audience berbeda secara substansial, potensi skala independen, pemisahan pasar bernilai, atau strategy/IP memerlukan isolasi.
4. Child tidak otomatis approved: butuh distinct customer/problem, economics, owner, market separation rationale, preliminary naming checks, domain/handle rights, serta legal/IP status.
5. Jika rights belum jelas: HOLD_FOR_RIGHTS. Jangan meluncurkan nama/endorsement atau membeli banyak domain spekulatif.

Mode parent-native memakai HOLBERY langsung; endorsed menggunakan hubungan yang terbukti; independent mempertahankan identitas sendiri namun tercatat di registry. Tidak ada kewajiban menempelkan HOLBERY pada semua child.

## Library-to-Brand Promotion Gate

Before proposing a child brand, record the item's Library category, lifecycle stage, customer/problem, evidence, economics, owner, rights, and reason for separation. If the separation case is weak, keep the item HOLBERY-native.

## Approval gate

Proposal wajib sembilan field PROJECT NAME, CATEGORY, OWNER, STATUS, PARENT, REPOSITORY, DOMAIN, CUSTOMER TYPE, REVENUE MODEL; tambah customer evidence, rights, visibility, dependencies, budget, review date, retirement trigger. Approve hanya untuk langkah yang scope-nya jelas (discovery, experiment, launch), bukan approval permanen tanpa review.

Master brand usage mengikuti promise/voice pada BRAND-FOUNDATION. Child boleh berbeda bahasa/visual; parent tidak menimpa customer equity. Campaign tidak mengubah struktur. Product/system memakai nama fungsi sebelum invented brand. Internal/experimental names tidak diubah demi kosmetik; tidak ada impor proyek privat.

## Operational governance

Review bulanan: opportunity cost, demand, outcome, revenue/margin/support, rights, status, dan next decision. Semua perubahan material masuk DECISIONS. Registry punya satu ID per proyek. Approvals legal/destructive (spin-off, transfer, lisensi eksklusif, penghapusan data) memerlukan user approval terpisah.

## Anti-fragmentation checks

Tidak menciptakan master brand saingan. Tidak menduplikasi target/problem tanpa alasan. Tidak mengklaim owned company/registered trademark dari strategi saja. Tidak mengonversi Bozq One System menjadi produk publik. Evidence review tidak sama dengan legal clearance. Website hanya memperlihatkan penawaran yang statusnya jujur.

## Repositories dan organisasi

Pertahankan Sparkmind-obp-off/Holbery sebagai master repo. Satu child repo baru hanya jika lifecycle, permissions, deployment atau ownership memang terpisah. Tidak membuat GitHub organization tanpa keputusan pemilik; gunakan existing account sementara. Hak public access code tetap tunduk lisensi; repository publik bukan izin penggunaan IP tanpa batas.
